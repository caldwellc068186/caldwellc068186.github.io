摘要

服务端要判断"这台设备跑的还是不是我发出去的系统"，客户端的自报答案没有价值：上报代码本身就运行在可能被改过的环境里。Android 的解法是一条把信任从硬件锚点传到服务边界的链——引导加载程序校验验证元数据，元数据描述各分区的摘要与哈希树，内核据此做运行期校验，启动结论由硬件后端的密钥层写进证明，服务端凭证书链读取启动状态、锁定状态与补丁级别。本文拆解这条链的机制与失效点，给出服务端的分层策略与评估顺序，并说明其固有局限。

关键词：验证启动；信任根；哈希树；回滚保护；密钥证明；远程密钥配置；服务端信任策略

一、设备完整性为什么需要一条可验证的信任链

1.1 自报状态不构成证据

任何"客户端上报自己安全"的设计都把判定权交给被判定对象：攻击者取得进程控制权后，最省事的做法不是破解加密，而是直接改上报字段——锁定状态、补丁级别、检测结果。密钥证明的不同在于报告由设备内的密钥硬件对服务端下发的一次性挑战值签名，应用无法指定签什么。

1.2 三个攻击层次

  • 改内容：替换分区中的代码或库，由启动校验与运行期哈希树负责。
  • 改观测：系统表面不变、只伪造检查结果，由硬件签名负责。
  • 换身份：借用另一台干净设备的证明能力为远程请求签名，密码学无法解决。

链条的目标不是让设备不可攻破，而是让"被攻破"在服务端可判定。

1.3 起点必须不可变

每一环只验证下一环的签名，全链安全性因此归约到那个不被验证的环节：片内固化的第一阶段代码与烧进一次性存储的公钥摘要。

二、启动链的各个环节

2.1 引导加载程序与信任根密钥

上电后片内代码校验一级引导加载程序的签名，后者再校验后续阶段与内核镜像；公开规范把这一过程组织为验证启动。引导加载程序还保护两件普通软件无法写入的持久状态：锁定位与回滚计数，解锁因此被要求实现为一次不可静默的操作。

2.2 验证元数据与描述符

"哪些内容可信"集中在一个被签名的顶层结构里，以几类描述符表达：

  • 整体哈希描述符：为必须完全加载的小块内容（内核与启动镜像）给出摘要，引导阶段直接比对。
  • 哈希树描述符：为可按需读取的大分区给出默克尔树根摘要与树参数，交内核逐块验证。
  • 链式分区描述符：把某分区的验证权委派给另一份独立签名的元数据，让平台方与硬件供应商各管一段。

2.3 分区哈希树与运行时校验

大分区无法在启动时全量读入做摘要，校验因此推迟到读取时刻：每读一块，块层沿哈希树向上算路径并与已认证的根摘要比对，保护是持续性的而非开机一次。代价是失败处理必须预先选定：返回输入输出错误、改为只读、记录后继续或停止启动。

2.4 回滚保护版本号

签名正确不等于版本最新：一个旧的、曾正常签名、已知有缺陷的完整镜像同样能通过检查。元数据因此带最低版本号，引导阶段将其与受保护存储中的单调计数比较，低于记录值即拒绝启动；正常更新推高记录值且不可回退。

2.5 解锁状态与数据擦除

切换锁定状态时多数实现被要求清除用户数据：允许任意镜像运行就无从阻止读取，只能让读取价值归零。但解锁只意味着链条不再由平台方背书，不意味着密钥硬件失效：解锁后仍能输出真实证明，只是启动状态字段显示未验证。

三、验证状态的含义与厂商差异

3.1 状态分类与信任含义

公开规范用有限几类状态描述一次启动结果（各实现取值命名有差异，接入时按实际返回值建映射）：

状态（概念）触发条件对服务端判断的意义
已通过全链校验成功，信任根为出厂锚点平台背书，可承载最高敏感度
自管信任根自行设置验证密钥，设备仍锁定发布者负责，只给条件性信任
未验证解锁，校验被跳过或签名不被信任链断裂但密钥硬件仍真实
失败不通过到无法安全继续不具评估价值

第二行常被忽略：组织用自有信任根交付同一镜像是合法状态，校验仍生效，只是背书人变了。

3.2 结论如何向上传递

公开实现把启动结论连同锁定状态与被验证内容摘要作为信任根信息传入密钥硬件并写入证明；同一信息也暴露为本机属性，但没有远端证据力。

3.3 关于差异的纪律

不同厂商与代次实现的可见字段、粒度与默认处置都有区别。"字段—取值—语义"映射表因此应作为接入方资产逐机型实测生成：判定只依赖经证明传递的签名内容，属性仅用于对照，冲突时按更低信任处理。

四、密钥层：证明链中携带什么

4.1 硬件后端密钥与链的锚点

应用生成密钥对时，私钥可留在硬件后端永不导出，随证书链返回的公钥绑定一组由硬件断言的属性。链的根决定服务端能声称什么：根可追溯到平台方的证明根密钥时，才得到"该平台认为此硬件处于可信执行环境"的断言；根为厂商自建且未登记时，平台对强度不作背书。

4.2 证明携带的信任信息

多数内容是条件性的，取决于生成时是否请求与实现是否支持：

  • 信任根：验证启动密钥标识、是否锁定、启动状态与被验证内容摘要。摘要对同一台原装设备应稳定；摘要改变而状态仍显示已验证，说明镜像或信任根变了。
  • 系统与补丁级别：引导、内核与系统版本，并分层给出平台级与供应商级，避免把驱动固件的滞后掩盖在一个总级别里。
  • 请求方身份：包名、签名摘要与版本信息，用于识别二次打包与克隆版本，需在生成密钥时显式要求纳入。
  • 设备标识：品牌、机型、序列号可为空，缺失正常，但意味着无法只凭证明完成设备唯一绑定。

4.3 远程密钥配置与轮换、撤销的难点

证明链的前提是设备里已有一把能签的证明密钥。出厂预置批次带来两个长期问题：数量有上限，用完即无法为新密钥出链；撤销依赖接入方主动拉取吊销状态。

较新平台把这套流程改为远程密钥配置：设备用出厂登记的唯一标识向配置服务批量换取短期证明密钥，接入方凭链中的层级结构逐级追溯到设备标识或其匿名代理证书。代价是把可用性绑到了服务存续上：配置服务通常只覆盖仍在支持期内的机型，设备停支持后批次耗尽且无法续期。

五、运行期完整性信号

5.1 分区校验失败的表现

失败很少以提示形式出现，更多是间接症状：只读分区文件读取报错、组件反复重启、崩溃集中在加载本地库处、块层出现哈希不匹配记录。这组症状本身就是完整性事件，不应只按应用稳定性处理。

5.2 可更新组件的影响

模块化更新把一部分内容移到独立签名与独立版本控制之下，仍在可验证体系内，但改变两件事：信任时点——启动结论只代表那一刻的状态，之后落地的组件若不被证明覆盖，判定就基于过期快照；粒度——级别字段能否反映组件更新取决于实现，应实测确认。此外，可写分区与外部存储上的代码可被本机任意改写，不能作为完整性依据。

5.3 调试接口与解锁并存

解锁意味着可改内容，调试接口与本地高权限意味着可读写进程与文件系统；二者叠加后攻击者不再需要漏洞利用链，所以分级依据必须是组合状态而非单个状态。本机自检可被绕过，二者冲突时以证明为准，并把冲突记为高风险事件。

六、服务端如何正确使用完整性信息

6.1 分层策略：拒绝、降级、增强监控

  • 拒绝：校验失败、证明不可解析、档位落在软件实现、根无法追溯到已知锚点、吊销命中。
  • 降级：保留功能但削弱能力——限制额度与频率、敏感操作重新认证、只发短期令牌；触发条件多为解锁、自管信任根、级别过旧但仍受支持。
  • 增强监控：放行但提高观测密度——记录启动摘要变化、对状态跃迁（锁定到解锁、摘要改变、级别下降）触发复核。

6.2 信号、可伪造性与可用策略

策略选择的依据是"谁能伪造这个信号"，而不是它听起来是否权威。

完整性信号能被谁伪造服务端可用策略
应用自报的属性与检测结果任意本机高权限者只用于冲突告警
未绑定挑战值的历史证明持旧链者离线重放一律拒绝，要求新密钥与新挑战
证明中的信任根字段需换密钥硬件或根签发能力核心依据，按状态分档
补丁级别与版本字段链内不可伪造，可停在旧版本设最低线，旧版本走降级
包名与签名摘要重签名会被暴露拒绝非官方签名实例
自建信任根的定制镜像内容由发布者决定只在登记清单内放行
云机与真机代签密码学上不可识别结合行为与账号风控并限流

6.3 证明不是唯一防线

证明回答的问题很窄："某个硬件在某时刻声明了这些内容"，它不回答设备此刻是否由申请人持有、请求是否来自同一网络与行为模式。三种过度依赖需要否定：只在首绑时验证一次后凭长期密钥放行；把"锁定加已验证"当作替代鉴权与输入校验的理由；把证明当设备唯一标识。

与企业侧结合是自然延伸：设备管理掌握注册与合规状态，证明掌握启动结论，二者互为佐证；当管理系统报告"已被强制解锁"而证明报告"已验证"，冲突本身就是最有价值的告警。证明适合作为设备可信度分档的一维输入，不适合作唯一准入闸门。

七、评估方法与局限

7.1 验证一台设备声明的顺序

  1. 取链解析：确认拿到完整证书链，并确认承载断言的扩展位于链中哪一张证书。
  2. 验链：逐级验证签名，把根追溯到已知锚点，区分平台方与厂商自建锚点，执行吊销状态检查。
  3. 验时新性：挑战值必须是本次下发的一次性随机数。
  4. 看档位：落在软件档位的密钥一律按不可信处理。
  5. 读字段：启动状态、锁定位与摘要是否符合目标档位，并与官方镜像摘要比对以识别替换。
  6. 做实验：在测试机上依次解锁、刷自定义镜像、设自建信任根、降级旧版本，确认字段随之变化。

7.2 不可验证的边界

三类设备在方法上就不可判定：无硬件密钥后端或缺少证明能力的老设备；字段完全由定制镜像决定的自建信任根设备；无法完成远程密钥配置的设备。第三类最易踩坑：若干年后会突然"拿不到证明"，若把证明设为硬性唯一条件，就会误剔除仍安全可用的设备；应按可验证性分层建档并预留降级通道。

7.3 证明被滥用的可能

两类滥用需正面承认：租用状态干净的整机为远程客户端代生成密钥与签名，使一批请求看起来来自合规设备；泄露的预置密钥遇上不做吊销检查的服务端，形成可持续的伪造通道。前者不是密码学问题，收益来自数量与自动化，反制在吞吐限制、行为特征与账号—设备关系的历史一致性。

八、治理建议

依赖设备完整性的业务方：

  1. 把"字段—取值—语义—机型"映射表版本化，逐机型实测生成，禁止按品牌写死规则；解锁与自管信任根默认走降级。
  2. 强制一次性挑战值与新鲜度窗口，禁止复用历史链；吊销与有效期检查作为在线依赖，并准备服务不可达时的兜底——宁可降级，不可静默放行。
  3. 为远程密钥配置迁移保留新旧两套验证逻辑；把完整性判定与生命周期绑定，超出支持期的设备即使字段全绿也视为风险递增。

设备与系统侧：保持解锁与数据擦除的绑定并说明后果；让运行期校验失败可观测、可分类；允许组织设置自有信任根，但如实反映"信任根已替换"。

九、结语

设备完整性的难点不是"能不能校验镜像"，而是校验结论能否跨越本机边界、在不信任的环境里仍被当作证据。这条链的分工是：硬件锚点保证起点，签名元数据与哈希树保证内容与运行期读取，回滚计数堵住降级，密钥硬件把这一切压进一份可远程验证的签名，服务端再用分层策略把它接住。

它也有止境：证明不了使用者是谁，也覆盖不了能力缺失的老设备与自行定义信任根的定制镜像。真正被滥用的环节很少出在密码学结构上，更多出在有人缓存了旧证明、跳过了吊销检查。
