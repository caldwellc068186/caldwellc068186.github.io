摘要

运行在车辆座舱与物联网场景中的 Android 设备，与手机共享同一套框架代码，却处在完全不同的工程与责任结构里：终端生命周期远长于平台支持周期，更新窗口受车辆状态或生产运行约束，安全责任在平台方、整机方、模组方与运营方之间多层切分，而公开安全公告恰恰覆盖不到风险最集中的定制层。本文从机制层面梳理其风险来源与治理框架：攻击面如何随架构改变，更新与补丁的现实约束，供应链治理，以及量产前后的准备与运营。

关键词：车载 Android；物联网终端；生命周期错配；OTA 更新约束；接口抽象层；供应链治理；漏洞运营

一、为什么非手机形态的风险更高

1.1 生命周期与支持周期错配

手机的安全节奏建立在两个默认假设上：活跃使用期有限，且厂商会在期内持续交付补丁。车载与行业终端的服务寿命通常以十年计，远超平台版本或上游组件的支持周期。终端还在运行，依赖的系统早已停止演进：新缺陷没有补丁来源，知识随人员交接流失。

1.2 更新通道的结构性弱点

手机更新由厂商直接掌控、用户确认即装。车机端，一次发布常牵连跨控制器版本兼容性验证，安装还要求驻车、供电与网络条件，用户可长期暂缓；物联网端，终端由运营方管理，更新意味着停机窗口与现场成本。"能更新"与"愿意更新"是两件事，设计时必须把低更新率当常态。

1.3 物理可达与多用户共享

手机大部分时间在持有者控制之下；车机停在路边、进入维修车间、经历二手过户，物联网终端常部署在无人值守或半公开场所，威胁模型必须包含具备时间与工具条件的访问者。这类设备还天然多人共享，数据主体是复数，账号残留与清除问题比手机严重。

1.4 安全责任主体分散

手机的安全责任名义上集中在整机厂商；车载与物联网侧，平台维护方、整车厂、模组厂与运营方各持有系统的一部分。切分本身不是问题，未书面切分才是：缺陷落在哪个代码域、由谁复现、由谁发布修复、由谁触达用户，任何一环没有归属，外部报告就会在链路里空转。可见，非手机形态的风险差异是结构性的，而非程度性的。

二、架构差异带来的攻击面变化

2.1 虚拟化与资源隔离

座舱域整合的常见做法是让 Android 以虚拟机运行在管理程序之上，与仪表等其他域共享 SoC 及显示、输入等外设；具体拓扑因方案而异。信任边界由此延伸到虚拟机之间与外设直通：隔离策略配置质量、共享设备后端与跨域通道，都可能比 Android 域内部更早决定安全水位。虚拟化不等于安全：过宽的外设访问与域间通道仍会让域内失陷向外传导。

2.2 车辆与外设接口抽象层

按 AOSP 的公开设计，车载硬件抽象层（VHAL）把车辆能力建模为一组属性，框架层服务向应用提供对这些属性的读、写与订阅。它也集中了责任：哪些属性可读可写、要求什么权限、对接车辆功能域的转换组件是否独立校验。粒度不当或缺校验时，抽象层就成了放大面——应用侧看似无害的接口，翻译到车辆侧可能敏感得多。物联网终端同构：厂商 SDK 的传感器与执行器接口常缺少统一权限语义。

2.3 诊断与维护通道

车辆存在独立于信息娱乐系统的诊断与维护体系，公开规范层面有统一的诊断服务接口分层。治理上要回答两个问题：Android 域是否有可从诊断或维护通路触达的暴露面；维修工具权限授予服务体系而非车主，信任模型里多出一类"持有特权工具的专业操作者"，其账号管理与审计常被忽视。本文只要求这些通道被登记、鉴权与审计，不讨论其使用方式。

2.4 语音、传感器与屏幕外交互面

攻击面不再以屏幕为中心：语音管线持续摄入环境数据；手机伴侣应用与投屏通路让命令从另一设备跨域进入；无人值守终端的本地网络服务长期监听。这些输入面的共同点是缺少"用户有意识操作"这一天然检查点，意图解析与授权判断只能由系统内部完成。

三、更新与补丁的现实约束

3.1 更新窗口

公开的车载方案资料描述了利用车辆闲置时段执行系统更新的机制：安装任务被调度到驻车、电量与网络条件满足的窗口。车机更新因此不是纯技术问题：补丁从发布到装载隔着验证、排期与用户意愿三层缓冲，物联网侧的停机顾虑造成同样延迟。风险评估应按"相当多设备数月后仍运行旧版本"做保守假设。

3.2 分区与回滚

A/B 分区与启动校验的思路在车机上同样适用，但回滚的权衡不同：整车软件与车内其他域存在版本配合关系，回退可能落到不再兼容的版本，因此平台方与整机厂通常倾向严格锁版本、禁止回滚。副作用是修复回归时无法快速退回，验证必须前置，发布周期被拉长。

3.3 责任切分

手机侧补丁分工基本两层：平台方公告，整机厂商集成。车机与物联网侧，一条缺陷链路可能横跨平台框架、定制层、抽象层转换组件、模组固件与云端服务，归属不同主体、节奏互不等待。危害不在"没人修"，而在分段修复之间缺少联合发布协调：框架补丁到了而定制层未适配，单点修复即告失效。对策是书面责任矩阵加联合发布约定。

3.4 公告覆盖不到的定制层

手机用户可凭安全补丁级别了解框架层修复进度，车机与终端的关键风险却沉淀在公告之外：厂商自定义服务、抽象层转换组件、闭源 SDK 与模组固件。这些代码没有公开公告，多数没有外部可见的版本—修复映射，运维方与用户无从判断设备是否已含某个修复。非手机形态的安全工作因此不能围着公告转，而要自建补丁台账与面向用户的安全通告。

四、供应链与预装组件

4.1 模组与整板供应

通信、座舱类模组常以成品形式提供固件与精简系统，整机方拿到的是二进制加文档。安全能力事实上分布到模组供应商手中，但采购往往只覆盖功能验收，不覆盖固件更新路径、缺陷上报入口与支持年限承诺。对策是把安全条款前置到选型：更新机制、修复时限承诺、组件清单与停支时间线都写进合同。

4.2 芯片供应商 SDK 与闭源库

图形、编解码等栈闭源交付是常态，非手机形态下占比更高、暴露性质不同：座舱里的闭源组件可能直接触及车辆属性通路，物联网的闭源库可能长期持有网络连接。无法通读源码时，治理转向外围：登记闭源工件的归属与版本，要求供应商提供物料清单与补丁承诺，运行期以最小权限或独立域收敛其活动空间。

4.3 软件物料清单的作用与局限

SBOM（如 SPDX、CycloneDX 格式）回答产品是否含某组件、版本多少、进入了哪些车型或批次，是影响面判定的地基。局限同样明确：自动生成的 SBOM 常漏掉静态链接与内嵌副本；它是构建时快照，不反映运行期配置，也不回答"该组件在这台设备上是否可达"。把它当成治理的全部，是登记一半问题就宣布解决。

4.4 监管与标准框架

部分市场的车辆型式准入已要求制造商证明具备经评估的网络安全管理体系与软件更新管理能力（对应 UN R155 与 UN R156），工程方法论层面被广泛参照的是 ISO/SAE 21434；消费类物联网亦有 ETSI EN 303 645 等安全基线标准。这些框架的意义不在引入新的漏洞类别，而在把漏洞处置、更新管理与供应链管理变成需要留痕、可审计的程序性义务，也决定缺陷发现后设备群获得修复的速度。

五、量产前应当完成的工作

5.1 威胁建模与滥用案例

建模从资产与暴露面开始：接口清单、数据流、信任边界，再引入滥用与误用案例，补足"合法功能被非法使用"的谱系——例如远程控制功能被用作监视。每条结论要么对应一个缓解设计，要么对应一个验证用例，要么被明确接受并记录理由；只产出风险矩阵的建模等于零。

5.2 接口暴露面清单

量产前用自动化手段生成暴露面全集：监听端口、导出组件、无线通道、调试与诊断入口，每项标注必要性、权限要求与责任人。其价值在量产后显现：每次发版重跑并做差异比对，就能抓住"非本意出现"的接口——测试服务漏进量产版本是最常见的自伤。

5.3 密钥与身份管理

共享默认凭据与硬编码密钥是经典失败模式：单台设备提取的密钥对整批设备同样有效，个案缺陷直接升级为群体事件。机制上缺一不可：设备唯一身份与密钥、受控签发流程、尽量落在硬件支持密钥存储中的保管、明确的吊销路径；并规划轮换与设备退出服务时的凭据处置。

5.4 现场调试通道关闭

量产下线必须包含显式的关闭环节：调试连接通道禁用，或改造为需要独立鉴权且留有审计的开启方式；日志收缩到不含敏感数据；测试签名与演示应用移除。这一环节应由发布流水线自动校验——依赖人工确认的步骤，在赶工期内都会失守。

5.5 下线与召回机制

最常被省略的是退出计划：支持周期的对外声明、终止支持前的用户触达、退役时用户数据的可验证删除、设备侧证书与云端凭据的同步吊销。对存在严重缺陷的设备群，需有软件侧补救与用户告知的明确通道。对物联网产品，"卖出去"与"负责到最后"之间这段路，恰是责任最含糊的区段。

六、量产后的运营

6.1 漏洞接收通道

可达、可用、有回应的报告入口是运营地基：公开安全联系方式与协调披露说明，内部明确谁受理、谁复现、谁回复，并承诺安全通信渠道、限期响应、善意报告不诉诸法律。大量长生命周期设备卡在这一步——报告无处可发，信息要么长期无人知晓，要么被直接公开。

6.2 分级响应

定级不能只看技术分数：实际风险由暴露面（可否远程触达、处于什么网络位置）、受影响功能与可用的临时缓解共同决定。中等评分的缺陷落在无人值守、长期联网的终端上，可能比孤立环境里的高分缺陷更紧迫。可行做法是预定义分级响应模板——远程缓解、热修复、随下个更新窗口、记录并接受——并让"暂不修复"成为有责任人、有复核期限的显式决策。

6.3 跨车型与跨批次影响面判定

同一平台软件会进入多个车型与批次档位。收到缺陷描述后能否快速回答"哪些设备在运行、哪个构建包含该代码路径"，取决于版本管理而非安全分析能力：构建基线、SBOM、配置暴露清单齐备，判定就是一次查询；缺失，判定就是一次考古。批次差异必须记录在案，否则修复发布后连"漏掉了哪些设备"都无法核实。

6.4 面向用户的安全状态提示

用户与运营方无法凭空感知设备安全水位。建议设备与配套应用以通俗方式展示当前安全版本、最近更新与支持状态；更新前讲清驻车要求与短暂不可用等影响；车队、租赁、过户等场景提供账号与数据随使用者更替而清除的入口。透明度不修复漏洞，但它决定补丁到达率，而到达率决定暴露窗口。

七、常见误区对照

误区机制层面的事实
手机侧流程与检查单可直接复用到车机与物联网生命周期、更新窗口、责任结构三项前提都变了，检查单必须重建
跟随平台方公告即等于完成安全工作公告不覆盖定制层、抽象层组件、闭源 SDK 与模组固件
采用了虚拟化隔离，攻击面问题即告解决隔离是策略属性，外设共享与跨域通道配置不当仍会传导
加密强度足够，密钥管理就算合格缺少每设备唯一性与吊销通道时，单机提取即等价群体暴露
生成了 SBOM，供应链风险即已登记在案SBOM 存在粒度、时效与可达性三重局限，只是治理起点

八、结语

非手机形态 Android 设备的风险有一个共同来源：平台演进快，设备走得慢；框架层补丁可见，定制层不可见；技术边界画得清，责任边界画不清。工作因此不同于单点漏洞研究：更有效的产出，是把暴露面登记、密钥治理、影响面判定与报告通道逐一想清楚，让发现缺陷后的每一步都有归属和期限。一个有用的判据是：在没有公告可依的设备上，安全工作本质上是在为自己建造一套公告体系。它平时看不见价值，只在缺陷出现的窗口里，决定还在服役的大批设备是被修复，还是被遗忘。
