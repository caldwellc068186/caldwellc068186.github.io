摘要

Android 设备的安全边界并不止于操作系统框架层。设备厂商在 AOSP 之上叠加的定制分区、硬件抽象层（HAL）、闭源驱动与基带固件，共同构成了实际运行在用户手中的系统，也构成了与 AOSP 明显不同的攻击面。同一版本的 Android 在不同机型上可能存在完全不同的缺陷，这正是固件层安全研究的价值所在。本文梳理一条可复现的固件安全分析工作流：在授权范围内使用合法获取的固件，完成镜像提取与分区解包，将攻击面映射到可调用入口，再在隔离实验环境中做最小化动态验证，最后按协调披露流程形成可修复的报告。文末面向设备厂商与集成团队给出工程侧的收敛建议。

关键词：Android 固件安全；系统镜像分析；super.img；AVB 验证链；vendor HAL；SELinux 策略；漏洞复现；协调披露

一、为什么固件层值得单独研究

AOSP 的安全公告按月发布，但设备真正收到的补丁取决于厂商的集成节奏。用户在"Android 版本"之外能看到的"安全补丁级别"，反映的正是这段滞后。滞后期内，框架层漏洞是否可被利用往往还取决于厂商的定制实现，而定制层本身还带来新的缺陷来源：

  • 厂商自定义系统服务与 HAL：这些实现通常不在公开代码仓库中，缺少社区审计，输入校验和权限判断最容易出问题。
  • 内核与驱动：厂商为摄像头、显示、音频、传感器等增加的驱动代码，多数使用 C/C++ 实现，是内存安全缺陷的高发区。
  • 特权应用：以 signature|privileged 权限运行的预装应用，可以触达普通应用无法访问的系统接口，其导出组件与参数处理逻辑等价于系统层的入口。
  • 基带、安全处理器与其他协处理器固件：独立于主处理器的执行域，一旦存在缺陷，影响面与主系统隔离策略同时失效。

因此，固件分析不是为了重复框架层的研究，而是为了回答一个更具体的问题：在我手上这台设备里，框架层的防护被厂商实现削弱了没有，以及厂商自己引入了什么。

需要强调的边界：本文讨论的方法只适用于自己拥有或已获得书面测试授权的设备，以及厂商公开发布的固件包。分析结果用于报告与修复，不用于访问他人设备或数据。

三、提取与解包：从更新包到可读文件树

第一步是把压缩与分块层次剥开。 稀疏格式（sparse image）需要先转换成原始镜像，否则文件系统工具无法直接读取。super.img 承载动态分区，实际包含 system、vendor、product、system_ext、odm、vendor_boot 等多个逻辑分区，需要用逻辑分区工具按布局拆出每个分区，而不是整体挂载。带虚拟 A/B 压缩（VABC）的更新包还要先解出 C 合并时展开的数据块，才能还原目标分区内容。

第二步是启动镜像与内核。 老格式的 boot.img 包含内核、ramdisk 与二级页表；采用通用内核镜像（GKI）的设备把核心内核与厂商模块拆开，需要分别取 boot.img 与 vendor_boot.img，其中 vendor_boot 里通常带有厂商的 lt-dtbo、DTB 与 ramdisk。解包后用 CPIO 归档工具还原 ramdisk，检查 init 脚本与 *.rc 中由属性触发的服务：这些服务往往以高权限启动，且读取外部可控属性，是入口枚举的重点。

第三步是文件系统读取。 无论 ext4 还是 EROFS，都应以只读方式提取内容，避免修改访问时间或元数据破坏可复现性。提取后先做目录级差异比较：与同族机型的固件对比、与上一版本对比。跨机型差异通常指向厂商定制代码，跨版本差异通常指向补丁改动——后者甚至能反向定位未被公开描述的修复点，是研究的高价值线索。

关于验证链的现实约束。 Android Verified Boot（AVB）对关键分区做哈希树签名，vbmeta.img 汇集各分区描述符与滚动版本号。这意味着研究时不能假设"改了 system 还能正常启动"：修改分区而不更新 vbmeta，设备会验证失败或降级；关闭验证通常要求解锁 bootloader，而解锁本身会触发厂商的数据擦除与安全状态变化，某些机型解锁后还会主动削弱或改变被测配置。因此固件静态分析与设备动态验证要分开规划：静态分析在离线镜像上完成，动态验证在明确接受解锁副作用的实验机上进行，并在报告中说明实验条件是否影响结论适用范围。

四、审计定位：把攻击面落到可调用入口

拿到文件树只是起点，真正的工作是把"哪些代码接收跨信任边界的数据"列成清单。可行的枚举路径：

  1. 接口清单。VINTF manifest 声明了设备提供的 HAL 版本与接口；framework 侧的 service list / dumpsys -l 给出运行期服务。两者交叉可以识别厂商私加的接口与只在特定机型上出现的服务。
  2. 权限边界。用 sepolicy 分析工具反查：哪些域可以调用该服务，哪些标签被允许执行敏感操作，是否存在宽泛的 allow 规则或例外宏。策略宽松往往等价于漏洞可达性提升。
  3. 入口点。SELinux 上下文里的设备节点、/proc 与 /sys 接口、属性前缀、广播与 ContentProvider，每一个都是外部可控数据的入口。对每个入口记录调用方权限要求。
  4. 可达性判断。导出组件是否要求系统权限，服务方法是否校验调用方 UID/包名，Binder 参数是否校验类型与长度，驱动 ioctl 是否校验用户指针范围与结构体版本字段。缺校验的入口优先深入。
  5. 根因归类。把可疑点归入既有缺陷类别（越界读写、释放后使用、整数溢出、竞态条件、类型混淆、权限检查缺失、路径遍历、签名校验绕过等），并记录可获得的利用能力：信息读取、任意写、代码执行或持久化。归类后再看平台已有的缓解机制是否压制。

这套方法的价值在于可迁移：同一份清单可以逐版本重跑，用差异驱动增量审计，而不是每次从零开始通读代码。

五、静态深入：HAL、内核模块与特权应用

vendor HAL 是固件审计中性价比最高的目标。它们直接接收来自 framework 或应用侧触发的数据，常用 C++ 手写序列化逻辑，且往往缺少框架层的统一防护约定。审计时重点看边界处：参数尺寸换算、共享内存与 fidl/parcel 句柄生命周期、异步回调的引用计数。AOSP 为部分 HAL 提供了模糊测试桩，厂商实现应当纳入同样的测试覆盖；如果目标固件中没有对应测试件，这本身就是可以反馈给厂商的改进项。

内核与厂商模块的审计依赖设备树与模块列表：确认哪些模块可被非特权进程打开，哪些 ioctl 命令号缺少最小权限检查。具备条件时应使用带检测机制的内核构建（例如开启 KASAN 或硬件内存标签的调试镜像）复现越界访问，因为生产镜像上的症状常常只是"服务重启"，检测构建能把症状变成可定位的报告。

特权预装应用常被忽略。它们运行在同一份 ART 上，却持有普通应用没有的权限。用反编译工具提取后，重点不是业务逻辑，而是导出的 Activity/Service/Receiver/Provider、隐式 Intent 的处理、以外部输入拼接的 PendingIntent、以及把外部数据转交给系统服务的桥接路径。这类缺陷通常不需要内存破坏即可获得权限提升效果。

六、动态验证与最小化复现

动态验证的目标是证明影响，不是制造破坏。工程上建议遵守几条纪律：

  • 隔离环境：实验设备关闭蜂窝与共享，接入隔离网段，不登录个人账号，不放入真实凭据与生产数据。
  • 可回滚：每次验证前保存分区快照与构建指纹，出问题能还原，也保证结论对应明确版本。
  • 最小可行性验证：优先构造能证明能力的证据，例如读取一个只有系统权限才能读的属性、向自身进程的可控内存写入模式，而不是追求完整利用链。报告里说明"能达到的最坏影响"与"验证到的程度"之间的差别，是最诚实也最专业表达方式。
  • 观测优先：logcat、tombstone、dmesg、系统调用跟踪四件套足以覆盖多数场景。竞态与状态相关缺陷需要重复触发与时序放大，把复现概率量化写进报告，便于厂商评估修复优先级。
  • 不要在生产配置上测破坏性用例：会触发重启或数据丢失的验证应在实验机上进行，并预先告知可能的后果。

七、报告与协调披露

一份可被厂商直接用于修复的报告通常包含：

  1. 环境与版本：机型、构建指纹、安全补丁级别、是否解锁、实验条件差异。
  2. 影响描述：触发该缺陷的权限前提，可达路径，能造成的最坏后果，是否需要用户交互。
  3. 复现步骤：从干净状态开始、可重复执行的步骤，附关键日志片段。
  4. 定位线索：涉及的分区、进程、接口与代码位置（在闭源组件上，至少给出符号地址与函数特征）。
  5. 缓解与修复建议：输入校验点、权限检查补充、是否需要收紧 SELinux 策略或禁用调试接口。

披露节奏上，通过厂商安全应急响应团队或平台方既有漏洞提交渠道报告，遵循协调披露的时间约定（通常以补丁可用为公开前提，公开细节推迟到修复分发后）。在补丁落地之前，不发布可直接用于攻击的利用代码、不提前公开完整技术细节，也不在设备上验证与缺陷无关的访问能力。

八、面向厂商与集成团队的收敛建议

固件层风险的治理，可以按下列优先级推进：

  • 缩短补丁滞后：把"安全补丁级别"作为发布门禁指标，对超期未合入月度补丁的机型给出明确说明与支持终止日期。
  • 保持镜像一致性：确保出厂镜像与更新包同源可校验，记录每次发布的构建指纹与镜像哈希，便于第三方核对与分析。
  • 给定制代码补测试：把厂商 HAL 与服务纳入模糊测试与静态分析流程，沿用平台已有的测试桩与加固编译选项（栈保护、_FORTIFY、位置无关代码、控制流完整性，以及 arm64 的指针认证与分支目标识别）。
  • 收紧权限面：审查 sepolicy 中的宽泛规则与例外；特权预装应用只声明必要权限，导出组件默认不导出，跨进程调用校验调用方身份。
  • 关闭生产调试通道：默认不启用高速调试接口与非必要属性写入路径；解锁策略与验证链降级行为对用户透明可见。
  • 把研究者的产出变成流程：建立对外报告入口、复现验证与反馈闭环。固件层缺陷大多来自少量重复模式，一次系统性整改的收益远高于逐条修补。

九、结语

Android 的实际攻击面由厂商定制决定，固件与系统镜像分析把研究视角从"平台公告"拉回到"手上这台设备"。合法取得固件、以只读方式解包、用清单驱动审计、在隔离环境做最小化验证、按协调披露交付可修复的报告——这条工作流并不依赖秘密手段，依赖的是版本记录、入口枚举和可复现性这些枯燥却决定结论质量的细节。对研究者而言，它是把发现转化为防护改进的路径；对厂商而言，它应当成为内部质量流程的一部分，在外部报告到达之前完成同样的检查。
